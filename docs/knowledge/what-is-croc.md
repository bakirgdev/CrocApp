# What is croc

Facts verified against croc **v11.5.4**, the pinned version: source read in the Go module cache, CLI behaviour checked in `src/cli`. Run `croc-upgrade-playbook.md` before trusting any of this against a newer croc.

Source: https://github.com/schollz/croc

## Identity

CLI tool to "easily and securely send things from one computer to another": any file/folder/text, between any two machines, via a short code phrase. Author Zack Scholl (schollz). Go, MIT license, actively maintained. No port forwarding or local server needed. Inspired by magic-wormhole; adds resumability, multi-file transfers, and full-duplex relay comms. A browser client lives at getcroc.com.

## How a transfer works

1. **Code phrase**: a generated code is three random words from the EFF short wordlist #1 (1296 words), joined by hyphens (`codephrase.Generate`). Custom via `--code` (min 6 chars) or `CROC_SECRET` env var. Older `NNNN-word-word` style codes still parse (legacy split, see step 2). **On Unix `send --code X` in the default (non-classic) mode exits without sending and tells you to use `CROC_SECRET=X croc send ...`; a receive code given as an argument is refused the same way** (`croc --classic` lifts both). Always prefer `CROC_SECRET` for scripting. The receiver takes the code as one argument, or as three or four arguments joined with hyphens.
2. **Rendezvous**: both sides connect to a relay and join a room named `SHA-256(selector + "croc")`. The selector is the first word of a three-word code, the first two words of a four-word code, and the first 4 characters for any other code (legacy). Practical implication: two concurrent transfers whose codes share the selector, on the same relay, collide into one room ("room full"). With generated codes that is about 1 in 1296 per relay; custom codes and test scripts must differ in the selector. **Relays**: with no `--relay`/`--relay6` (or `CROC_RELAY`/`CROC_RELAY6`), no `--local` and no `--ip`, the CLI uses a public pool, `1.getcroc.com:9009` to `4.getcroc.com:9009` (`publicrelay.Relays`). Both sides pick the relay from the code: `RelayIndex` = SHA-256 of the whole code as a big-endian integer, modulo 4. A sender with no custom code uses the relay cached in a `best-relay` file in croc's config dir, or else probes all four (1 s timeout) and caches the first to answer a ping, then generates codes until one maps to that relay (`GenerateForRelay`); a send on a generated code that fails with a relay connection error clears the cache. The pool path blanks the IPv6 relay. The old single default still exists: `models.DEFAULT_RELAY` `croc.schollz.com:9009` and `DEFAULT_RELAY6` `croc6.schollz.com:9009` are what `--relay`/`--relay6` default to. Transfer ports default to 9009-9013 (control port first).
3. **PAKE**: the passphrase part of the code (the final two words of a three-word code) feeds PAKE2 (`github.com/schollz/pake/v3` v3.2.0, Boneh-Shoup construction) through `src/pakekey`, which binds the exchange to the purpose, room, and role of each side. Default curve P-256 (`--curve`: p256, p384, p521, siec, ed25519). Yields a strong session key from the weak phrase; relay never learns it. The peer PAKE protocol is versioned (`pakekey.ProtocolVersion` = 2) and fails closed on a mismatch.
4. **Encryption**: end-to-end. The PAKE session key goes through HKDF-SHA256 with a 32-byte salt and a transcript of both PAKE messages, the room, curve, and identities (`pakekey.Derive`), giving a 32-byte traffic key plus two key-confirmation keys; each side proves it holds the key (HMAC-SHA256 tags) before data flows. Everything on the wire after that is **AES-256-GCM** (`crypt.NewAESGCM`, random 12-byte nonce prepended per message). `crypt.New` (PBKDF2-HMAC-SHA256, 100 iterations) now only protects the client-to-relay password handshake (`src/tcp`), not transfer data. `crypt.NewArgon2` (Argon2id → XChaCha20-Poly1305) and `EncryptChaCha`/`DecryptChaCha` exist in the same file but have **no non-test call site in v11.5.4**, so do not describe croc as Argon2- or ChaCha-based. Relay sees ciphertext only: untrusted by design.
5. **Transport**: files DEFLATE-compressed (HuffmanOnly, `--no-compress` to disable; a file whose first 256 KB shrinks by under 2% is sent uncompressed), chunked at 32 KB. Two paths for the data, chosen by the sender with `--transport` (`auto` default, `derp`, `relay`; receivers always follow the sender):
   - **relay**: chunks are claimed from a shared queue by up to 8 parallel TCP connections, one per relay transfer port. This is croc's classic speed trick.
   - **Tailcat** (`auto` tries it first, `derp` requires it): two native v11 clients build PAKE-bound node identities and carry TCP streams over an in-process userspace WireGuard network that starts on DERP and moves to direct UDP when NAT traversal works. A browser peer, an older client, or a failed setup falls back to the relay ports; `derp` disables that fallback, and `--transport` cannot be combined with `--local` unless it is `auto`. A build without Tailcat downgrades `derp` to `relay`.
6. **Local path**: sender also starts a local relay and broadcasts its port over UDP multicast (`schollz/peerdiscovery`, default group 239.255.255.250 via `--multicast`, IPv4 and IPv6). The receiver races discovery (200 ms search, 500 ms cap) against the relay dial, 75 ms staggered; whichever connection completes first wins, and if the relay wins the receiver still asks the sender for its local IPs and tries them directly. Same-LAN transfers never touch the internet. **Discovery is not guaranteed**: seen once on an AP/client-isolation-style network where multicast discovery returned zero peers every time, for both the stock CLI and crocmobile (previous croc pin, not re-tested on v11); root cause not isolated. Workaround: `--ip <senderLAN-IP>:9009` on the receiver connects directly to the sender's local relay control port (the first local relay port, 9009 unless busy) and skips discovery entirely, without touching the public relay.
7. **Resume + integrity**: interrupted transfers resume (receiver scans the partial file for zeroed chunks); an existing file of the same size is hashed and skipped when equal. Hash: xxhash default; imohash (sampled), md5, highway via `--hash`.
8. **Reconnect**: a dropped transfer is retried up to 10 times with a backoff of 100 ms doubling to a 5 s cap, each attempt in a fresh random room; after that it fails with `transfer disconnected after 10 reconnect attempts`.

## Feature surface (GUI must eventually cover)

- Send: files, folders, multiple files, raw text (`--text`), piped stdin, zip-before-send (`--zip`), exclusions (`--exclude`, `--exclude-file`, `--git`)
- Receive: `--yes` auto-accept, `--overwrite`, `--rename` (receive an existing name as `name (1).ext` instead of prompting), output dir (`--out`), `--stdout`
- Code: random, custom (`--code`), env (`CROC_SECRET`), QR code of the web receive URL `https://getcroc.com/?code=...` (`--qrcode`), code copied to the clipboard by default (`--disable-clipboard`)
- Transport: custom relay (`--relay`, `--relay6`, `--pass`), self-hosted relay (`croc relay`, min 2 TCP ports, `--ports`, `--transfers`, admission limits), data path (`--transport auto|derp|relay`), SOCKS5 proxy incl. Tor (`--socks5`, relay DNS resolved by the proxy), HTTP proxy (`--connect`), upload throttle (`--throttleUpload`), curve + hash selection, local only (`--local`)
- Stored transfers: `croc store` (or `send --store`) uploads client-side-encrypted files to a service (default `https://getcroc.com`) for a limited number of downloads (`--downloads`, default 1) and lifetime (`--expiration`, default 1d); receive from the printed link or token, revoke with `--revoke`. Separate from the live PAKE protocol.
- Shared terminal: `croc ssh` hosts or joins a terminal with six-word invitations over a Tailcat path, relay fallback.
- IPv6-first (50 ms head start), IPv4 fallback

```bash
croc send file.txt                                   # -> prints word-word-word
CROC_SECRET=word-word-word croc                      # receiver (Unix)
croc --relay myserver:9009 send f                    # self-hosted relay
```

## Security history

2023 (v9.6.5 and earlier): a security review led to CVE-2023-43616..43621, covering dangerous file overwrites and zip extraction among others, and the secret visible in the process list to local users (CVE-2023-43621, why Unix needs `CROC_SECRET`). Fixed in v9.6.16, a breaking protocol change that upstream re-released as croc 10.0.0. The v11 repo references no formal audit. GUI implication: croc's threat model assumes an untrusted relay and trusted endpoints, so CrocApp should surface receive confirmations and never invent auto-accept defaults.

## Facts relevant to CrocApp

- Importable as Go library: `github.com/schollz/croc/v11/src/croc` (`croc.New(croc.Options{...})`, or `croc.NewCtx(ctx, opts)` to pass a context, which crocmobile uses). Pure Go + x/crypto, gomobile binding works. New `Options` in v11: `Transport`, `Rename`, `PublicRelay` (set when the relay came from the pool; it only changes the receive hint the sender prints).
- Peers need croc 11 or newer. A v10 and a v11 peer cannot complete a transfer: v11 rejects a PAKE message without protocol version 2 (`peer uses unsupported PAKE protocol version 0; upgrade both croc clients`), and v10.5.0's `message.Message` has no version field at all. The v11 key schedule differs from v10's as well. The peers often never meet at all (v10 derives the relay room from the code's first 4 characters, v11 from the first word, and v10's default relay is not always the pool relay a v11 code maps to), so `peerVersion` fires only when both reach the same room.
- croc's README lists a community native Kotlin client (`croc-app`, F-Droid) that is not in-repo; `docs/knowledge/prior-art.md` covers its subprocess architecture, unusable on iOS. The README also lists `croc-desktop` (Wails, in-process croc) with experimental iOS/Android; no dedicated free native iOS client is listed, so CrocApp fills a real gap.
- Likely iOS friction points: UDP multicast discovery (needs `com.apple.developer.networking.multicast` entitlement) and listening sockets for the local relay.
- Default relay password constant `"pass123"`; `TCP_BUFFER_SIZE` 64 KB; chunk size 32 KB.
