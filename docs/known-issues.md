# Known issues

Triaged defects, accepted papercuts, and deferred work in the shipped app. Every item here was found during review and consciously not fixed. None block V1 unless marked.

This exists so a session does not re-discover and re-report the same thing. If you fix one, delete the line. If you decide one is permanent, move it to "Accepted" and say why.

Engine and bridge invariants live in `knowledge/crocmobile-bridge.md`; UI state-machine facts in `knowledge/app-ui-architecture.md`.

## Blocking release

- **Export compliance rests on the open-source exemption.** Both app `Info.plist` files set `ITSAppUsesNonExemptEncryption` to `false`, because `true` makes App Store Connect refuse the upload without an `ITSEncryptionExportComplianceCode` (the first upload attempt failed that way, 2026-10-14). `false` relies on croc's standard encryption having public source (EAR 742.15(b), the owner's 1.0 decision). Confirm it before Submit for Review: re-read App Store Connect's encryption questions and check France, which asks for an ANSSI declaration; if App Store Connect requires it, leave France out of 1.0 and file a `future` issue. If the exemption does not hold, set `true` and add the `ITSEncryptionExportComplianceCode` App Store Connect issues after approving documentation (`docs/BUILDING.md`, section 7, "Export compliance").

## Harnesses

- **`verify-interop.sh` can still lose the receiver-first race.** Its scenarios start the receiver after a fixed `sleep 3`, and croctest has no ready marker; on 2026-10-13 a public-pool run failed `relay 1: wrapper custom-code send` with `flate: corrupt input before offset 6` on the CLI receiver, and the retry passed. Port a ready signal from croctest (for example its `EVENT code` line) if it recurs.
- **`verify-app-mac.sh` exits with no `FAIL:` line when a CLI receive fails** (`recv_from_app`, under `set -e`). Its log is still in `$TMPDIR`. `verify-share-sim.sh` and `verify-interop.sh` already report this case.
- **No harness proves a LAN-discovery transfer on a custom multicast address.** croc drops discovery packets from its own host's addresses, so two peers on one machine never find each other (CLI to CLI included). `verify-interop.sh` scenario 15 instead listens on the group and asserts what each side announces. A real two-device check on a shared non-default group is not done.
- **A delegate panic in `OnCodeReady` leaves a text send's temp file behind.** `startSession`'s uncommitted cleanup removes the zip, cwd and lock but not `tempPath` (`crocmobile/session.go`). Found by `TestNetworkGlobalsRestoredAfterPanic`; harmless in the app (the file sits in the temporary directory), not fixed in B19.
- **`BUILDING.md` §5's `croc relay` runs whichever `croc` is first on `PATH`.** On a machine set up with `CROC_V10` at `~/go/bin/croc` ahead of Homebrew, that is v10, which rejects `--source-join-limit`, and every scenario then fails `connection refused`. Run `"$(brew --prefix)/bin/croc" relay ...` there.
- **On the development Mac, `croc --transport derp` CLI to CLI does not complete.** 130 MiB failed twice with `DERP connection failed: peer connection: dial Tailcat streams: context deadline exceeded` after 10 s, while all four `*.ipn.dev` DERP hosts answered HTTPS (200). Cause unknown; both peers on one host is a suspect, not proven. On a physical iPhone `derp` completed (owner, 2026-10-14, `knowledge/device-test-checklist.md`, "Transport and Tailcat gate" (d)), so Tailcat's data path works on iOS and the gate passed. Under `auto` on the Mac the relay carries the data, so transfers succeed, and `verify-interop.sh` scenario 13 and `verify-app-mac.sh` scenario 8 only assert the `tailcat-offer`, not that Tailcat carried the bytes.

- **The release workflow has not run yet with signing.** `.github/workflows/release.yml` was only exercised through `scripts/build-devid.sh` locally. Run the first `workflow_dispatch` rehearsal from `main` after the P06 merge (dispatch needs the workflow on the default branch, and the `release` environment allows `main`), and check it before tagging a release.
- **`release.yml` passes the `.p12` password and the throwaway keychain password on `security` argv** (`security import ... -P`, `security create-keychain -p`, `unlock-keychain -p`, `set-key-partition-list -k`). `security` has no stdin option for them, so other processes on the runner can read them while the command runs. Acceptable only on a single-tenant runner. Do not run this workflow on a shared runner.
- **`release.yml` installs `create-dmg` unpinned** (`brew install create-dmg`), and `scripts/build-dmg.sh` runs it while the signing keychain is unlocked and the notary `.p8` is on disk. A compromised or broken formula update would run with access to both. Accepted for 1.0: Homebrew offers no simple version pin for a formula, and a version check would fail every release after an upstream bump. If that changes, pin it in a version file like `scripts/croc-v10.version`.
- **The first local Sparkle update test hung after "Install and Relaunch".** In the update test (`docs/BUILDING.md`, "Testing a Sparkle update locally"), run 1, the very first launch of the `com.bakirgdev.CrocApp.direct` bundle ID on that Mac, downloaded and prepared the update, but after "Install and Relaunch" the app never terminated. Its own Quit menu item was then ignored too (main thread idle), and the installer kept waiting. The next 4 runs passed, 3 of them with Sparkle's first-launch defaults deleted, so first-launch state alone does not explain it. Cause unknown. If it recurs, watch `log stream` for `org.sparkle-project.Sparkle` and for the app's termination, and repeat the release rehearsal from a clean macOS account.

## Design system

- **The paste button in `CodeField` is 38 pt, below the 44 pt hit-target rule.** The component spec in `CodeField.swift` sets it, and `design/accessibility.md` says 44 pt for anything interactive. One of the two documents has to change. Found in the B23 accessibility pass, not changed there.
- **Small status glyphs use fixed point sizes.** `StatusBanner`, `StatusBlock`, `TrustBadge`, `FileRow`, `OnboardingView`, `ContentView` and the direction arrow in `TransferStatusView` set `.font(.system(size:))`, so they do not track Dynamic Type, against `design/accessibility.md` ("App glyphs size by text style"). They are decorative or repeat a word next to them, so nothing is lost at large sizes. Predates 1.0; found in the B23 accessibility pass.
- **`FileRow` stats each file for its size label inside `body`.** `List` is lazy so only visible rows pay, but it is still synchronous I/O on the main actor during layout, and a network or iCloud volume could make it hitch. Not measured.

## Landing page

- **The primary CTA's two store badges still resolve to nothing.** "Download" in the hero scrolls to three channels; the GitHub releases link works now that v0.9.9 is published, but the two store badges stay unlinked until the apps ship. The release it reaches is ad-hoc signed, so Gatekeeper refuses it on first launch until notarization is real — the release notes carry the Privacy & Security route.
- **The disk image background is 1x only.** `create-dmg` documents png, gif and jpg backgrounds, so `assets/dmg-background.png` has no HiDPI representation and reads soft on a Retina display. Fixing it means a multi-representation TIFF, which `create-dmg` does not document and which has not been tested here.
- **`--content-max-width` on the hero mockup.** `design/web.md` now carves an explicit exception for elements that depict the app, so this is documented rather than fixed — but the exception is narrow and easy to over-apply.
- **Store badges are inverted in dark mode with a CSS filter.** Apple ships black and white variants; the repo has black only. Inverting a black-on-transparent badge produces the white variant, but it is a filter over supplied artwork, not the supplied artwork.
- **`llms.txt`'s release status is hand-maintained and nothing checks it.** It has to be edited by hand on every release. The JSON-LD `dateModified` used to sit beside it and has been dropped: it rotted on every commit that touched the page, templating it from `git log` puts a moving part inside a structured-data block where a broken template corrupts silently rather than failing loudly, and `datePublished` alone is true forever. `og.jpg` is a second hand-made asset but a deliberate one, fixed rather than rotting.
- **The landing and docs pages set no Content-Security-Policy.** GitHub Pages cannot send headers, so only a `<meta http-equiv>` CSP is possible, and it needs a hash for each inline script (the theme script on every page, the code parser in `r/index.html`, Docusaurus's own inline scripts) that must be regenerated on every edit. No injection sink exists today: `r/index.html` and `app.js` write with `textContent` and build links with `encodeURIComponent`, and nothing loads third-party script (`web/` review, 2026-10-15, W1). Recorded rather than fixed for 1.0: a wrong hash breaks the page silently in the browser, and `scripts/assemble-site.sh` does not yet check it. Clickjacking of the `/r/` buttons stays open either way, since `frame-ancestors` is ignored in a meta tag.
- **`/r/` accepts any fragment of six or more characters without whitespace as a code**, so `/r/#download` offers to open "download" in CrocApp. Display only; the text is escaped and the app validates the code (W5).
- **The AASA file claims `/r/*`**, wider than the one page that exists. `/r/x` is a Pages 404, so no real link is taken (W6). `security.txt` expires 2027-08-01 and needs renewing before then (W7).

## Docs site

- **No site search, on purpose.** A local search plugin is a new dependency and Algolia DocSearch is an external account plus a third-party request from a page that makes a privacy claim. Sixteen pages with a full sidebar and browser find-in-page is enough for now. Revisit if the page count grows.
- **The version dropdown is invisible.** Docusaurus hides `docsVersionDropdown` while only one version exists; it stays hidden until the first `docusaurus docs:version` cut.
- **A landing-only change rebuilds the docs site too, and vice versa.** `github-pages.yml` calls `scripts/assemble-site.sh`, which builds both surfaces regardless of which one changed.
- **Eleven of the eighteen screenshot pairs are unused.** `scripts/capture-screenshots.sh` writes eighteen light/dark pairs; the README, six docs pages and the landing hero between them reference seven. The rest are deliberate headroom, not waste — adding a usage is cheap, re-capturing a deleted one is not.
- **The two sitemaps stay separate.** `web/landing/sitemap.xml` is hand-maintained and lists the one landing URL; `robots.txt` advertises the Docusaurus-generated `/docs/sitemap.xml` alongside it, so crawlers reach both. Not a defect with a single landing route — the `lastmod` that used to rot there has been dropped.
- **The docs build is not fully pinned.** `packageManager` in `web/docs/package.json` has no `+sha512` hash, so the workflow's corepack fetch is not integrity-checked (`corepack use pnpm@<version>` writes it); the four `overrides` in `pnpm-workspace.yaml` are open-ended `>=` floors; and `pnpm audit --prod` reports one High advisory with no fix, `braces@3.0.3` (GHSA-vfj7-8cjw-p6xm, stack exhaustion), reached through chokidar and micromatch inside Docusaurus core. All build-time only; no attacker input reaches the glob handling (`web/` review, 2026-10-15, W3, W4, W9). Re-run the audit on each Docusaurus upgrade.
- **The Pages "cancel" step probably does nothing.** `github-pages.yml` posts to `pages/deployments/$SHA/cancel` and ends in `|| true`; `github.sha` is a commit, not a Pages deployment ID (inference, not tested), so a cancelled run may leave the deployment hanging (W8).

## Accepted

- **"Upload Symbols Failed" for `Croc.framework` (iOS) and `A` (macOS) on every App Store upload.** Xcode embeds a 50 KB stub `Croc.framework` dylib with no dSYM, because the gomobile xcframework is a static archive linked into the app binary, so there is nothing to symbolicate there. It is a warning of Xcode's upload step, not an ITMS warning, and the build still processes. Seen 2026-10-14, first upload.
- **When both relay addresses are customised, both are sent.** croc's own CLI blanks `RelayAddress6` whenever v4 is customised, without checking whether v6 was customised too (`src/cli/cli.go`, send and receive alike), so it silently discards a user's custom v6 relay. Keeping both is more correct, not less. The divergence is deliberate and is not going to be "fixed" toward the CLI's behaviour.
- **`dropDestination(for:action:isTargeted:)` stays at `ContentView.swift` and `SendView.swift`.** The Xcode 27 SDK marks it deprecated only for a future OS (`deprecated: 100000.0`), so builds emit no warning. The replacement `dropDestination(for:isEnabled:action:)` takes a `Void` action (a drop cannot be rejected) and has no `isTargeted`; its highlight API `onDropSessionUpdated` is iOS 27 / macOS 26 only, and the deployment target is iOS 26.0. Revisit when the minimum OS reaches 27.
- **`OutputFolderStore.select` silently no-ops if bookmarking fails.** Rare, and the alternative is an error path for a condition the user cannot act on.
- **A zipped-folder receive that collides with more than 4096 existing members still fails.** crocmobile answers croc's per-member `Overwrite '<path>'? (y/N)` prompts from a batch of 4096 lines written up front (`promptPolicyAnswers`), sized to fit a fresh pipe buffer on Darwin and Linux so the write never blocks. Past that, croc's unzip reads EOF and fails with `received archive failed validation or extraction`, leaving the received `.zip`. Accepted: a larger batch could block the write (`knowledge/crocmobile-bridge.md`).
- **The incoming sheet cannot preview which members of a zipped folder already exist.** The file list shows one `.zip` name, so the conflict scan sees none of its members and offers only Accept (Keep Both). The existing members are kept and the matching ones in the archive skipped under every policy, Replace and auto-accept included: the stdin answers croc's unzip prompt reads are always "n", because a queued "y" would also answer the accept prompt croc re-runs after a reconnect or forces when the sender ran `--ask` (`knowledge/crocmobile-bridge.md`). Accepted: the archive's contents are only known to croc after it unpacks, and keeping what is there loses nothing.
- **A file whose name ends in a space cannot be sent to a croc v11 peer.** CrocApp sends the exact name (crocmobile `splitPaths`, B22), but croc 11.5.4 receivers, CLI and crocmobile alike, refuse it: `unsafe receive path in "report.pdf ": Windows-trimmed trailing character`; the sender sees `cancelled`. Accepted: the refusal is croc's receive-path policy, and before B22 the send silently picked up the sibling file without the space. Rename the file to send it.
- **A croc v11 reconnect after a manually accepted receive ends as `refused`.** croc re-runs the accept prompt on the sender's file list after each reconnect (`resetForReconnectAttempt`, then `processMessageFileInfo`), and the next queued stdin answer is "n", so the receive fails instead of resuming. Accepted: answering "y" there would accept a list the user never saw (security scan F2, 2026-10-15), and crocmobile cannot tell that prompt from the unzip prompt on the same pipe. From reading croc v11.5.4; no harness forces a reconnect.
- **The trust badge names the configured route, not the path that carried the data.** `TrustBadge` reads the relay setting, so a transfer that croc moved over the LAN, or over Tailcat under Connection = Automatic, still shows "Via the public croc relay" (or the custom relay). croc does not report the winning path to the engine. Accepted: the badge's claim that the server sees only encrypted data holds on every path.
- **Receive list identity is by file name.** Duplicate names within one transfer are a croc-level concern, not a UI one.
- **Gesture-level flows are not machine-verified.** Drag-and-drop, camera QR, and taps have no XCUITest coverage, by decision: unit tests cover non-UI logic (Go `go test -race`, Swift Testing in `CrocKitTests` and `CrocAppTests`, all in CI), transfers are covered by the harnesses, and UI flows are verified by hand. The rule is in `CONTRIBUTING.md` (Verification, Tests).
- **`braces` <= 3.0.3 (GHSA-vfj7-8cjw-p6xm) has no patched release.** Stack exhaustion on deeply nested brace patterns; it is reached only at build time through `chokidar` and `fast-glob` over our own docs paths, never from user input, and no override can lift it. `pnpm audit` lists it, and any Dependabot alert for it is dismissed with this reason. Remove this item when `braces` publishes a fix.
- **`xfer()` has no watchdog.** If croc ever blocks past context cancel and prompt-pipe close, `activeMu` is held for the process's lifetime and every later transfer returns "another transfer is active". Accepted: forcing the lock open while croc is still running would let two sessions mutate the same process-global state (`os.Chdir`, stdin/stdout swaps).
- **`poll()` reads `croc.Client` scalar and slice fields with no synchronization** (croc's own goroutines write them unguarded). Degrades to inconsistent progress numbers; bounds-checked (`session.go`'s `progressSnapshot`) so it cannot panic. Accepted: the writes are croc's, so a fix needs upstream locking, and the worst case is a progress number that is briefly wrong.
- **The harnesses fail at random against the public relays when they rate-limit.** Accepted: the limit is relay policy, and CI does not depend on it. A croc v11 relay admits 30 connections a minute from one address (`DEFAULT_SOURCE_JOIN_LIMIT`, `DEFAULT_JOIN_LIMIT_WINDOW`), and a multiplexed transfer opens 9 per peer (1 control, 8 data), so with both peers on one machine two transfers on the same pool relay inside a minute can be refused with `relay admission rate limited`. `verify-interop.sh`, `verify-app-mac.sh` and `verify-share-sim.sh` then fail at whichever scenario hits it; on 2026-10-12 back-to-back `verify-interop.sh` runs failed at scenarios 6, 7 and 10 (then the pool scenario, now 11) this way, and the pre-v11 runs saw the same thing from `croc.schollz.com`. `verify-interop.sh` scenario 11 waits 60 s and turns multiplexing off for that reason. CI avoids this: its `interop (local relay)` job runs `verify-interop.sh` with `RELAY` set to a local `croc relay` with raised admission limits (`docs/BUILDING.md`, section 5). The other harnesses have no local-relay mode yet, so use a local relay for a deterministic result, leave a minute between public-relay runs, and treat a failure as a regression only after finding the cause in its log.
- **A generated-code send with no internet or no reachable pool relay fails before a code is shown.** With default settings, no pool relay answers the 1 s probe (`crocmobile/relay.go` `generatePublicCode`), so the send fails with code `noPublicRelay` (croc's `no public relay available`, the same as the v11 CLI). A "draw a code anyway and let a LAN peer join" fallback was tried and removed: after the relay dial fails, croc waits for a LAN peer for only about 10 s (`defaultAlternateSenderRouteTimeout`, unexported, `croc.go:58`), and a `croctest send -relay 127.0.0.1:1` with no receiver printed its code and failed about 11 s later. Workaround: turn on **Local network only** (`troubleshooting.md` "Relay unreachable"). The app shows "No public relay answered. Check your internet connection, or turn on Local network only in Settings if both devices are on the same network." Accepted: the same behaviour as the v11 CLI, now with its own message.
- **A receiver that joins before the sender fails with `flate: corrupt input before offset 6`.** The receiver's `pake1` local probe times out after 500 ms, it carries on with the main PAKE, and the sender's late reply to the old probe is decoded as a transfer message (`knowledge/crocmobile-bridge.md`, croc gotchas). Generated codes are sender-first, but custom codes are not: a receiver who types an agreed code before the sender taps Send, or an app receiver waiting on a CLI sender using `CROC_SECRET`, hits it. The user sees the generic failure copy. Workaround: start the sender first, then the receiver. No upstream issue found in `schollz/croc` (searched 2026-10-13); a draft is not filed. Accepted until croc fixes it upstream: the probe timeout and the frame decoding are croc's. `verify-share-sim.sh` and `verify-app-mac.sh` start their CLI receiver 3 s after the app's `verify-code-ready.txt` marker for the same reason.
- **A transfer with a croc 10 peer usually shows no error and waits until the user cancels.** The app reports `peerVersion` ("peer uses unsupported PAKE protocol version 0; upgrade both croc clients") only when both peers reach the same relay room. Cause: croc v10 derives the room from the code's first 4 characters (`src/croc/croc.go:249`, `SharedSecret[:4]`), v11 from the first word of a three-word code (`src/codephrase/codephrase.go:194-222`, `Parse`, both read from source, not run), so an app-generated code lands in a different room than a v10 peer computes unless the first word has exactly 4 letters. The v10 CLI's default relay `croc.schollz.com:9009` is the same server as pool relay `1.getcroc.com` (142.132.189.179) but not pools 2-4, so only codes that map to pool relay 1 meet. Verified 2026-10-13 by runs: over a shared relay with a legacy-format code (for example `7020-alpha-beta-gamma`) the app gets `peerVersion` in both directions, and the v10 CLI prints `could not secure channel` (as sender) or `broken pipe` (as receiver); a v10 send on default settings reached the app via 1.getcroc.com and got `peerVersion`. Accepted, not fixable on our side: a v10 peer cannot be changed and the room and relay derivation are croc's. Workaround: the v10 side upgrades to croc 11.
- **Cancel during a generated-code send's relay probe waits up to 1 s.** The probe in `startSession` runs on `context.Background()` (`publicrelay.ProbeTimeout`), so Cancel takes effect when it ends. Cancelling through `startSession` needs a cancellable context threaded in. Accepted: the wait is bounded by the probe timeout.
- **`HistoryStore.clear()` has not been watched emptying the list without a relaunch.** It uses `delete(model:)` on `container.mainContext` and saves immediately, from a `@MainActor` type. Apple documents that deletion via that method takes effect on the next save, which is satisfied, and the known `@Query` refresh asymmetry is about *inserts* from a background `ModelActor` context, not main-context deletes. Accepted: correct by construction, and no harness drives History. Fallback if it ever misbehaves is a fetch-and-delete loop. Save and fetch failures are logged (`os.Logger`, category `history`).
- **`UIFileSharingEnabled` is declared twice**, in `app/Config/CrocApp-Info.plist` and as a pair of sdk-scoped `INFOPLIST_KEY_*` settings in the pbxproj. Accepted: the plist declaration is the one that works. Removing it drops the key from the built `Info.plist` entirely and takes the app out of the Files app, even though `xcodebuild -showBuildSettings` resolves the build setting to `YES` (measured on a simulator build). The pbxproj pair is inert for this key and harmless; drift risk only, since the values agree.
- **The macOS local-network denial path is hard to exercise during development.** Accepted: a development-procedure note, not an app defect. Enforcement reportedly only engages for builds resident in `/Applications` (single developer-forum thread FB16077972, not Apple documentation — strong inference, not verified here), so a DerivedData-launched Debug build can sit at `.ready` and read as falsely granted. Copy the app to `/Applications` before trying to reproduce a denial.
- **`AppRouter` is a singleton with no reset hook, so multiple macOS windows share one navigation path.** Accepted: per-window navigation needs `@FocusedValue` plumbing to reach `AppDelegate` and `Commands`, which sit outside the environment graph, and multi-window reachability has never actually been observed. Revisit if someone reports it.
- **croc prints the code phrase, and a non-default relay password, to stderr on every send.** croc builds the "On the other computer run" line (`croc <code>`, plus `--pass <password>` when the password is not the default) with `Quiet=false`, which crocmobile needs (`knowledge/crocmobile-bridge.md`), and its debug logger prints file names and paths. Nothing in the app captures stderr: a build launched from Finder, the Dock or the Home Screen has it connected to `/dev/null` (strong inference, not measured on a device), so it reaches no log store or crash report. A harness run or an Xcode debug session does capture it (`verify-app-mac.sh` writes it to its temp logs). Accepted for 1.0; revisit if croc gains a way to silence that line without `Quiet`.
- **Deleting a stored upload's History row removes the only Revoke button.** The receipt stays in the Keychain until the link expires, but nothing lists receipts without a record. Deferred: revoke before deleting the row. Revisit if users lose links this way.
- **The Camera app cannot open CrocApp for a stored link.** The stored link points at the transfer server, and Associated Domains covers only `crocapp.dev/r/*`, so a camera scan opens the server's page in the browser. In-app Scan QR Code and Paste work. Accepted for 1.0.
- **The menu-bar window cannot take a drop on the icon itself.** `MenuBarQuickSendView`'s drop zone exists only while the window is open, so a user has to click the icon first and then drop. A `MenuBarExtra` has no drop target on its status item. Accepted: the window opens with one click and the "Choose Files…" button needs no drag.
- **A Shortcuts send action returns at the code, not at the end of the transfer.** `SendFilesIntent` and `SendTextIntent` finish when `awaitCode()` sees `.waiting`, so a shortcut that goes on to quit CrocApp, or a user who closes it, ends the transfer before the receiver has the files. The dialog says "Keep CrocApp open until the transfer ends." Accepted: the code has to reach the receiver while the sender is still waiting, so the action cannot wait for the end. Receive does wait for the end. Neither the actions nor the Finder Quick Action have been run on a device (`knowledge/device-test-checklist.md`, "Shortcuts actions (R27)").
